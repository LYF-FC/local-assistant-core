# 031 — Reviewed synthetic Work restore quarantine

Outcome: before exposing a restored synthetic database to applications/workers, a trusted operator names the restored database and workspace, previews access/session metadata, then explicitly applies the exact reviewed quarantine. Atomically disable that workspace, delete all its Work grants and revoke every unrevoked platform session belonging to those grantees. This signs affected users out across scopes; unrelated users/sessions/workspaces and private Work content stay unchanged. No data leaves the local environment.

Require matching development/test target, disposable test naming, explicit restored-database name matching configured and actual database, synthetic workspace and clean READ COMMITTED owner of registry/users/sessions/audit. Explicit active technical-admin operator is an audit reference, not HTTP human proof. The acknowledgement identifies the chosen target, not proof that a database is actually a restore or its latest state.

Acquire the exclusive registry barrier before workspace/user/session locks. Lock grantee and operator user rows in UUID order (matching login's user-before-session order), then sessions; protect the operator scope membership. At most 25 grantees and 100 unrevoked sessions per operation; fail closed without truncating if exceeded. Metadata-only canonical plan binds database name/OID, workspace, operator, enabled state, grantee IDs, session IDs/user/expiry/last-seen and server issue time. No slug, label, credential, token/CSRF/content hash or private content. At most 32 KiB. Apply requires exact digest and aware fixed server issue time no older than five minutes, rechecked before commit. Changed access/sessions/time/target, replay and empty no-op reject before mutations.

Registry deletion, session revocation, workspace disable and metadata-only admin.work_restore_quarantined receipt share one transaction. Any audit/guard/timeout/commit error rolls back; output follows commit. Receipt is evidence, not authority to enable. Concurrent cleaners serialize; in-flight authorized Work transactions finish or rollback before quarantine. New logins after quarantine may authenticate with unchanged passwords but have no grant to this disabled workspace. Other-session ordinary activity can cause a safe stale-plan/lock failure; preview again after stopping services.

No schema/grant/API/UI/dependency change, automatic daemon, reactivation, password/key rotation, note purge or old-backup suppression manifest. This is a manual offline recovery prerequisite, not an enforced startup quarantine flag or complete recovery certificate. Existing trusted administration can later change state; require separate reviewed acceptance before regrant/enable. Newer forgetting decisions, other restored workspaces, old jobs/approvals, credentials, sources, keys, derived stores, exports and full-host recovery remain separate gates.

Acceptance: real PostgreSQL exact-plan/session/grant changes, multi-session/shared-user effects, unrelated preservation, runtime/assumed-role/unsafe isolation/target/operator denial, bounds/time/replay, audit rollback and registry serialization. Actual CLI in migration container; actual restored database quarantine with retained redactions/content, revoked restored-session denial, disabled workspace/no grants and receipt. Existing full local checks and single exact-head four-job hosted readiness gate remain required.
