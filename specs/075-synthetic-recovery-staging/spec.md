# Spec 075 — synthetic recovery staging and restored database binding

## Authority, scope and outcome

The owner authorized implementation of this first synthetic-only restore/staging slice on 19 November 2026. This contract describes that bounded work; authorization is not evidence of implementation, integration, independent verification or acceptance. [PROJECT_MASTER.md](../../PROJECT_MASTER.md) owns project scope/status. [Spec 074](../074-recovery-set-manifest/spec.md) remains unchanged, including its point-in-time assurance, trust inputs and HMAC limitations. Spec 074/C1–C5 and every MVP gate retain their existing status.

Outcome: the disposable PostgreSQL recovery drill must consume exactly the staged synthetic dump bytes bound to a successful Spec 074 verification, then reject restored database identity/schema disagreement before downstream fixture checks. A manifest-authenticated declaration about an installation or migration head is not proof of the dump's database contents; this slice checks both in the restored isolated database.

No real key, real recovery set, production/private data, production/NAS storage, C4 measurement, capacity claim, operational restore, deployment, encryption/key-management workflow or general restore CLI is included. Synthetic keys may be made only by the existing test helper for this authorized engineering slice. No data leaves the disposable test boundary except non-sensitive test results. No new database schema, migration, permission model or application API is introduced.

## Clarified first-slice boundary

1. Extend a private internal Python helper and the explicitly disposable PostgreSQL test harness, not a user-facing operational recovery interface.
2. Inputs are synthetic files, an existing synthetic recovery key, explicit expected fingerprint, installation UUID, schema head and expected manifest hash. This first slice accepts dump-only sets (`expect_archive=absent`) and a dump of at most **16 MiB**, a deliberately small engineering bound, not a capacity/operational ceiling. Require `freshness_match` as equality to the explicit synthetic anchor; it is not proof of latest backup or independent governance.
3. Copy the dump-only set and manifest into a new private stage without overwriting anything or modifying the source. Verify the staged copy with the unchanged Spec 074 verifier and require integrity/authenticity/expectations/freshness success and verified references. Reject malformed references or missing verified dump hash. Archives are rejected by this first slice; do not install archive objects into an application archive.
4. Read the protected staged dump into a bounded immutable byte snapshot, compare its content SHA-256/byte count to the verified dump reference, then supply exactly that immutable snapshot as `pg_restore` standard input. Never reopen the original or staged path for the bound restore. Restore process failure must reject the target before any downstream checks.
5. Postrestore, compare actual singleton installation and Alembic state with the explicit trusted expectations that passed staged verification. Only synthetic structural binding can succeed. Release/adoption eligibility remains blocked for all results.

## Exact-byte assurance and limits

Spec 074 section 8 explicitly says re-verification immediately before reopening a path does not remove the gap. This contract therefore uses a bounded immutable snapshot checked against the authenticated staged dump digest, then supplies those exact bytes to `pg_restore`. Merely rehashing a path and later calling `pg_restore` on that path is insufficient. A pinned open file descriptor alone prevents pathname substitution but not in-place writes; the snapshot digest/count checks remain required. The test harness must not substitute different bytes between obtaining the snapshot and supplying standard input; immutable bytes avoid in-place mutation but do not constrain arbitrary caller behavior.

The stage and immutable snapshot provide a bound synthetic evidence chain; they are not a host security sandbox against a compromised kernel or same-user process. The helper inherits Spec 074's Linux `O_PATH` filesystem requirement; local macOS execution of staging is not supported by this slice. File checks/race assumptions must be stated by the implementation. Archives are outside this dump-only slice. No clean-host independence, configuration/credential/model recovery, complete archive usability, latest backup, RPO/RTO, restore duration, non-Work suppression or production safety is established.
