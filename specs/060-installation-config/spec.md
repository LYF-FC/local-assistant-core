# 060 — Installation identity, versioned defaults and setup readiness

## Specify

An authenticated technical administrator initializes an explicit installation-local UUID, previews/applies bounded versioned language/timezone defaults, inspects history, exports/imports a sanitized setup template and sees an honest read-only development capability/readiness catalogue. This advances INSTALL-01/02/03/06/08 foundations with synthetic data; no production/private adoption, live connector/model activation, secrets, new household grants or data migration. Nothing leaves the installation except explicitly downloaded non-secret templates.

## Clarify / checklist

- Migration 0030 seeds an unconfigured singleton revision 0 with no installation UUID/configuration/actor. No automatic identity creation by migration/read. First explicit apply mints UUID locally; later edits/imports preserve it. Independent template initialization mints a different UUID; restoring a private backup preserves the original identity. Existing member/scope schema, user IDs, namespace/refusal guards and all domain permissions stay unchanged; dynamic membership/onboarding and whole-installation isolation are separate gates.
- Only current `technical_admin` reads/configures/history/exports. Technical administration grants no access to unrelated private content. POST/Origin/CSRF/session/current-grant checks and user→singleton locks through audit commit; revalidate expiry after waits. Expected installation UUID+revision prevents cross-install/stale writes and concurrent initialization. No public bootstrap or new password/credential route; existing trusted account provisioning remains required.
- Configuration schema1 contains only defaults: ordered unique languages (one to three of en/fr/es; first preferred) and an explicit valid IANA timezone (64-character printable bound). No names, member IDs, host paths, endpoints, credentials, flags, arbitrary graphs or runtime records. Extra/malformed/unsupported keys reject before mutation. Defaults configure this setup record/template; existing per-record/user timezones remain explicit and are not silently rewritten.
- Preview returns exact normalized template/current source, changed-field summary and at most five-minute session/source/payload-bound receipt; preview audit must commit before release. Apply requires the same payload/UUID/revision/receipt/expiry and literal acknowledgement. Edits clear UI preview; no automatic mutation retries. Changed applies append protected history and metadata audit atomically; same-value apply is a no-op (does not consume history). At most100 revisions, history five/page; reads and sanitized export remain available at limit. Full installation deletion/decommission/history compaction is not introduced.
- Export is an allowlisted schema1 setup template with only language/timezone defaults, preceded by explicit copy/privacy acknowledgement. No source installation/user/workspace IDs, revision/actor timestamps, records, secrets or private host/account paths. Import preview shows exact fields/differences; template identity/foreign/private fields are rejected. Setup template is not a backup. Defaults can themselves reveal preferences/timezone: review them before sharing. Old downloads/backups remain outside recall.
- Readiness catalogue has stable capability keys, validated acyclic known dependencies and mandatory-core markers. It distinguishes development availability, operator setup, environment-disabled, configured-but-unverified and planned/authorization-required. It performs no network/filesystem probes and exposes no private paths/model names/endpoints/secrets. It is informational; no activation/disable switches or new route/worker enforcement are claimed. Environment configuration does not prove health, permission, license or live provider acceptance. Current runtime controls/consumers remain unchanged.
- Immutable singleton UUID/creation identity, increasing revisions, schema/payload bounds, actor/history matching, restricted runtime grants and no delete/truncate/history rewrite. Logical restore verifies UUID/defaults/history and sanitized-template boundary with no consumer activation. Migration/downgrade need protected backup and reviewed rollback; downgrade removes installation identity/config/history. Older binaries are not certified for continued settings writes. No private installation upgrade follows from tests.
- UI appears only to technical administrators, keeps drafts/receipts in memory, clears on session/view changes, preserves conflicts until explicit reload and clears sensitive results on denial. Mobile preview/apply/history/template export/import and late-response navigation must work. No secret-bearing URLs, local storage or echoed private validation input.

## Acceptance

1. Validation/normalization, unknown fields/versions/identities/secrets, preview expiry/payload/session/source binding and explicit acknowledgement, no-op/quota/history/export behavior.
2. Admin/non-admin/revoked/session/Origin/CSRF negatives, after-wait expiry, concurrent initialization/edits, audit failure rollback and sealed SQL grants/identity/history.
3. Two actual isolated synthetic PostgreSQL configuration datasets mint different IDs, sanitized template reuse preserves only defaults, foreign receipts/tokens cannot cross. This is configuration-boundary evidence, not whole-domain INSTALL-09 acceptance.
4. Migration round trip/full logical recovery preserve actual installation UUID/config/history without reinitialization or effect activation; downgrade/backup limitations documented.
5. Strict ephemeral client and trusted HTTPS/mobile setup lifecycle/conflict/view-clearing; default Compose migration ownerbutler/runtime refusal preserved. Native PG/restore deliberatelypostgres.
6. Required checks/privacy/security/canonical149-ID/dashboard/review consistency; one coherent commit/push/PR, expectedCI then stop without polling/merge.
