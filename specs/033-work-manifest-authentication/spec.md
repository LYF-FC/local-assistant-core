# 033 — Authenticated synthetic Work recovery manifests

Outcome: a trusted operator creates a separate workspace recovery authentication key, independently pins its public fingerprint, then exports/verifies/reconciles authenticated suppression files using that exact recovered key and fingerprint. Edited metadata, even with a recomputed unkeyed digest, fails before database connection. The existing owner/quarantine/exact-review gates still apply. No information leaves the local environment.

Use standard-library HMAC-SHA256, full 256-bit tags, explicit 32-byte OS-backed secrets generation and constant-time tag/pin comparisons. A domain-separated known-message HMAC over public key identity/namespace/time forms the public fingerprint; artifact MAC has a distinct domain. Key files contain version/mode, key UUID, workspace UUID, aware creation time and 32-byte material, with SecretStr repr/error masking. New-file-only 0600 persistence and protected owner/single-link/regular/no-follow reads reuse existing bounded durable file handling. Key file bound 2 KiB; authenticated manifest bound 32 KiB. No secret in CLI arguments, environment variables, stdout, database, audit or plans. Only key ID/public fingerprint are returned/recorded.

CLI generation is offline, workspace-bound and does not provision a database/provider key. Pin the fingerprint from trusted generation output independently of the database, key file and manifest. Every normal suppression CLI export/preview/apply requires an explicit protected key path plus expected fingerprint; never auto-adopt a pin from an input file. Verify key identity/pin/namespace and full authenticated envelope before database access. Unknown/missing/unsafe keys, wrong pin/workspace/key ID, malformed header, bad MAC, and unsigned legacy files reject. No blind signing/upgrading of arbitrary old files or unsigned-bypass flag. Re-export legacy files from a verified source; exceptional lost-source legacy recovery stays separately reviewed.

Authenticated version-2 envelopes wrap the unchanged bounded version-1 metadata manifest plus algorithm, key ID/fingerprint and MAC. Inner canonical digest is retained, not treated as authentication. Plans/receipts bind public authentication references alongside manifest/target/dependency metadata. Source audit records requested key reference and preparation only, not saved-file proof. Neither MAC nor secret material is copied to shared audit/plan. Privileged internal Python primitives remain trusted owner operations; default metadata marks them trusted_owner_input, not cryptographically verified. Public receipt/key references are not bearer permission or independent signed audit.

Existing source actual-terminal export, target disabled/no-grant state, active technical-admin audit reference, clean owner, row/global locks, conflict/caps/time/replay/no-op, atomic redaction/audit and downgrade behavior remain unchanged. No schema/grant/dependency/API/UI change, automatic key mount/provider, rotation/deletion of real credentials or production action.

This is symmetric authentication to a known key, not encryption, asymmetric signature, nonrepudiation, proof of source truth/human attention or latest-complete ledger. Any holder of the key can forge manifests; previously valid authenticated files can still be stale. Keep keys/anchors independently protected/recoverable; generate a new key/file for deliberate rotation and retain needed historical keys under separate policy. No automatic revocation/rotation registry or hardware/off-site key recovery claim. Document encryption, latest completeness, credentials/jobs/derived/unmanaged exports/full-host/actual M2 and real data remain gated.

Acceptance: key/file/header/domain/namespace/pin/MAC/secret-output negatives, recomputed-digest tampering and old-file rejection before DB access, real signed CLI review/apply/receipt plus unchanged owner gates, actual older-dump/newer-authenticated-file recovery after primary key file removal and independent test-copy recovery, migration-container generation/export/preview/apply/replay, full local and single exact-head four-job hosted readiness.
