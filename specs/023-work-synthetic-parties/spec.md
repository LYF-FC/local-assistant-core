# 023 — Synthetic workspace parties and explicit note owners

Outcome: the trusted local operator can create a bounded synthetic party in one active synthetic workspace, retire it, or forget its label. A note's explicit owner_id is an active, unexpired party UUID in the same workspace; it is never inferred from the author, authenticated user, household profile or text. Null remains unknown. These are local synthetic storage primitives before authenticated capture/party UI, not an application writer or real colleague directory.

Party identity is immutable: workspace/id/policy/creation time/retention and marker cannot be corrected or reassigned. Label is a 11–256 character synthetic marker. Explicit existing workspace retention policy bounds retain_until. New entries start active revision 1; terminal retire or forget requires exact expected revision. Retired can become forgotten; no reactivation. Forget sets marker null, retaining only minimal party identity/revision/time/policy metadata. Append-only private audit stores no marker. Existing note histories contain only the party UUID; retired/forgotten parties do not silently rewrite historical ownership. Read preview can still show that historical UUID, never imply current assignment authority. New create/correct/confirm with non-null owner requires current active/unexpired party; forget remains possible after retirement. No label is copied to note snapshots, public audit or family memory.

Migration 0013: private FORCE-RLS party/audit tables, owner-only mutations, immutable audit, registry-exclusive barrier before party mutations, same-workspace active-owner validation trigger on note writes. No API/runtime/read-role party grant by default. Local functions require typed UUIDs, matching development/test target, explicit READ COMMITTED transaction and clean actual table-owner connection; no SET ROLE residue. Private mutation/audit and minimal public operator audit commit atomically. No implicit identity grant, session impersonation, model, provider, background schedule or external transfer.

Migration rollback must refuse while current/history note snapshots retain owner UUIDs; deliberately forget affected notes first, then verified backup before dropping party metadata. Existing note forget scrubs all owner references/history. Same-database logical restore preserves active/retired/forgotten parties, label redaction and workspace/role denial. Independent key/older-backup/derived-copy/full-host recovery remains open. Expiry hides eligibility; it is not a physical deletion guarantee.

Acceptance: malformed marker/target/transaction/role/revision denial; create/retire/forget/audit atomicity; explicit valid/unknown ownership, missing/cross-workspace/retired/expired owner rejection at Python and direct SQL boundaries; no reactivation/identity/label/retention mutation or delete/truncate; role/RLS isolation; confirmation after retirement becomes denied without application; concurrent party mutation serialized against note writes; migration round-trip/downgrade guard, logical restore, make check and exact-head CI.
