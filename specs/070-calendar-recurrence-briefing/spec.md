# 070 — Calendar recurrence, provider-mode sync and briefing v2 (Batch 3)

Batch 3 of the agreed synthetic-MVP order (ORG-01/02, CORE-08/09, UI-01, MVP-02). The authoritative design is revision 11 of [the proposal](../../docs/BATCH3_CALENDAR_RECURRENCE_PROPOSAL.md); this spec records what was delivered, the guarantees, and every deviation or clarification. ORG-01 and MVP-02 stay **partial**: there is no live Apple/iCloud or Google/Microsoft read, no external write, no attendees, alarms, free/busy, travel or scheduling, and no model call. Everything runs on **synthetic data** through a read-only SQLite synthetic provider that exists only in development and test.

## What it delivers

- **All-day placement fix (G1).** An all-day occurrence is placed by its calendar dates only (`start_date <= day < end_date`, end exclusive), never by instants, so neither the event zone nor the display zone can move it. Timed events are placed by instant overlap as before.
- **Recurrence engine.** A strict, bounded RFC 5545 subset: `FREQ` daily, weekly, monthly or yearly; `COUNT` or `UNTIL` (not both); `INTERVAL`; `BYDAY` (weekly only, no ordinals); `BYMONTHDAY` (no negatives) and `BYMONTH`; `EXDATE`, `RDATE`; overrides by `RECURRENCE-ID`. Anything else is refused with a stable code, never approximated. Recurrence runs on wall-clock time in the event's zone: a generated wall time that does not exist (DST gap) or an invalid date (31 February) is ignored, not counted and never clamped; a repeated wall time takes the earlier instant. Routines keep their own, unchanged convention.
- **Provider mode.** A source declared provider-mode (dev/test only) is synchronized from a cursor-based provider into series, overrides, tombstones and a gapless change log (migration `0035_calendar_provider_sync`). Occurrences are expanded on read and never stored. Provider mode and manual import are mutually exclusive per source (database trigger).
- **Sync protocol.** T1 claim (lease, committed before the provider call), fetch outside any transaction with a timeout shorter than the lease, T2 apply (whole-page plan, deterministic write order, all or nothing) or T3 failure (backoff 30 s, 2 min, 10 min, 1 h; the fifth failure is terminal `failed`; blocked codes never retry on their own). One-shot worker `python -m app.calendar_worker --once`, compose service `calendar_worker` (profile `calendar`, no restart).
- **Forgetting.** One transaction scrubs every provider table; the deferred trigger refuses the commit if any step is missing. A forgotten source is never revived and every owner route answers the same 404.
- **Briefing v2.** Optional `horizon_days` (1 to 7; otherwise 422). The response keeps every v1 field and adds per-day summaries, per-source `source_state`, `as_of`, `blocked_reason`, recurring/exception/continues markers, `cancelled_count`, `possible_duplicate_of` (flag, never merge) and explicit `limits`. Browser results still expire within 60 seconds.
- **Routes.** `POST /api/v1/calendars/{id}/provider`, `/sync` and `/sync-status` exist only where the synthetic store is configured in development or test and are owner-only. `query` can expand provider sources over at most 400 days.

## Guarantee statement (at-least-once fetch, idempotent apply)

**Guaranteed:** a page may be fetched more than once; applying the same item more than once has the same database effect as applying it once (per-item sequence rule plus the unique change index); the stored cursor never points past changes that are not committed; a refused page leaves data and cursor unchanged; a forgotten source is never revived.

**Not guaranteed:** that the provider is queried only once per change (this is at-least-once fetch, **not exactly-once**); that a provider honours cursors or keeps tombstones; recovery of deletions missed while a cursor was lost; ordering between independent entities across pages; freshness better than the stale threshold; recall of anything outside the database (there is no external effect in this batch, and external writes are disabled).

Evidence: real-subprocess exits at every crash point P0 to P6 with a fresh recovering process, real-thread concurrency (a gated provider holding the lease, concurrent passes and owner syncs, forgetting racing a sync), an injected database failure mid-apply, and a real `pg_dump`/`pg_restore` round trip with a resumed sync from the restored cursor.

## Briefing v2 behaviour that needs stating

- **Per-source state is an enum**, never a boolean: `available`, `stale` (last success older than 24 h), `unavailable`, `blocked`, `unknown_coverage`, `limit_reached`. One source being down never hides another. A stale, unavailable or blocked source keeps its last data visible, labelled with `as_of` and its state. Coverage unknown is stated as unknown; no missing event and no household need is inferred.
- **Explicit limits.** `limits` reports `{shown, truncated, omitted_at_least}` for sources, events, tasks and memories plus `unreadable_items`. The version 1 `truncated` booleans are derived from the same counts. Events are `truncated` also when a series expansion hit its own bound. The silent slices of G13 are gone.
- **Corrupt stored data policy.** A stored item that cannot be read (a series or override that fails to expand, a malformed stored manual event, an unreadable window) is **counted** (`unreadable` per source, `unreadable_items` overall), forces that source to `unknown_coverage`, and is never dropped silently and never a server error. The remaining items of the source and all other sources are still shown.
- **Version 1 requests are unchanged.** Without `horizon_days` the response has `schema_version: 1` and exactly the v1 key set (an existing test pins it). `limits` and the other additions appear from version 2 on, so the v1 booleans are the only truncation signal there.

## Deviations and clarifications to revision 11

1. `recurrence_id` is the empty string for single events (the repository's legacy non-recurring form), so occurrence identity stays `uuid5(source.id, json.dumps([uid, recurrence_id]))` and no existing id changes. It does not appear in the provider tables.
2. `calendar_overrides` carries `deleted_at` (revision 11 refers to preserving it but lists no column). The replacement start is `start_wall` and `duration` is one column whose unit follows the series kind.
3. Forgotten series and overrides keep their non-content `sequence`; `recurrence_id` and `created_at` remain immutable. A forgotten source's scrub requires every series and override to be `forgotten`, so tombstones lose their `uid` too.
4. Beyond the revision 11 list, the guards require `revision = OLD.revision + 1` and a non-decreasing `updated_at` on every update of series, overrides and sync state; a strictly increasing `sequence` on every non-forgetting update; new sync-state rows start as `never` with empty counters; new series and override rows start at revision 1; `applied_seq` equals `max(seq)` on every sync-state update.
5. Refusals use SQLSTATE 23514 with the rule name in `CONSTRAINT`, so tests assert the exact guard.
6. The deferred orphan trigger reads the series state at commit. The commit 4 sync tests found a false positive (a series deleted and revived within one page); migration 0035 was corrected in place and recorded in [the F1 audit](../../docs/BATCH3_F1_AUDIT.md). Nothing had been pushed or merged, so no released migration changed.
7. The per-source briefing enum is named `source_state`: the receipt's `state` (`active`/`forgotten`) is the source lifecycle and must not be overwritten.
8. The provider, sync and sync-status handlers are registered always and answer an identical `404 Not Found` per request when the synthetic store is not configured in development or test (and are left out of the published schema). The external behaviour matches "the routes do not exist"; the difference is an implementation detail.
9. The sync route authorizes in one request transaction, runs one bounded pass outside it, then reports counts and codes in a second one. It never repeats the pass.
10. A defect in the forgetting scrub (override rows were updated from the series revision column, producing a cartesian-product update) was found by an SQLAlchemy warning and fixed in the commit that introduced it, with a regression test that fails without the fix.
11. **The fetch timeout terminates the fetch (review blocker, correction after PR #28 opened).** The first implementation ran the provider call on a `ThreadPoolExecutor` and gave up with `future.result(timeout)` plus `shutdown(wait=False)`. A running Python thread cannot be cancelled, so a sync was recorded as `provider_timeout` while the provider call kept running: one leaked non-daemon thread per timeout, and a worker that could not exit until the call returned. Protocol correctness held (the late result was discarded, T2 is guarded by claim token and stored-cursor compare-and-swap, the provider is read-only, the lease was already released by T3), but resource use and shutdown were unbounded. The fetch now runs the provider call in a forked child process: the parent waits with `Pipe.poll(timeout)`, sends SIGKILL at the timeout (which a provider cannot ignore), and reaps the child with a bounded join; the child also arms `signal.alarm(timeout + 1)` and leaves with `os._exit`, so even an abandoned parent leaves no lingering work. Lease (1..600 s, default 120 s) and fetch timeout (0 < timeout < lease, default 30 s) are unchanged, as are the three phases, the backoff ladder and the error mapping; only the inside of `fetch` changed. Consequences: the provider object is not pickled (fork inherits it), so test providers work, but a test double that coordinates with the parent must use a fork-context `multiprocessing` event, not `threading`; fork from a threaded process emits a Python 3.12+ `DeprecationWarning`, and the child only runs `provider.changes`, so a lock held by another parent thread at fork time can at worst stall the child, which the timeout and alarm bound to the same `provider_timeout` result.

## Test-suite findings (why earlier PostgreSQL runs flickered)

- `test_calendars_postgres` failed intermittently (`KeyError: 'window'`, a request that never reached its row wait). Cause: committed synthetic rows outlive a test in the shared database; the new PostgreSQL schema and sync tests left many active shared sources behind (some stored without the full source shape), and the briefing reads the first 25 active sources of the shared scope. The fixtures now retire what they create and use the full stored shape.
- Crash-point tests failed intermittently with a skipped sync. Cause: the crashed subprocess stamped its lease with the real clock while the fixture clock started earlier, so "lease + 1 second" could still look unexpired. The helper now moves the fixture clock to real time after the subprocess exits.

## Limitations checklist (not delivered, by design)

- No live Apple/iCloud, Google or Microsoft read, no OAuth, no external write, attendees, alarms, free/busy, travel or scheduling; ORG-01 and MVP-02 stay partial.
- Recurrence is the bounded subset above; unsupported rules block the source rather than degrade.
- A provider that loses cursors or tombstones can leave deletions undetected until a resync; resync is an explicit owner action.
- Per-source bounds (200 active and 400 total series, 100 active and 200 total overrides per series, 5,000 change rows, 400-day query, 7-day briefing) refuse rather than truncate on the write side and report on the read side; a retention/compaction design is still needed before long-running polling.
- The synthetic provider is read-only fixture data; it proves protocol behaviour, not provider behaviour.
- Process-restart evidence for the spec 068 and 069 workers is **not** retrofitted by this batch and is tracked as a separate item; this batch adds it only for the calendar worker.
- Duplicate detection across sources is a flag on same normalized title and overlapping interval; it never merges or removes.
