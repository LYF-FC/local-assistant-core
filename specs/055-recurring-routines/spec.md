# 055 — Recurring routines, generated tasks and private reminders

## Specify

A member previews and explicitly saves a finite daily/weekly routine, corrects its future schedule/template, pauses/resumes it, inspects occurrence/completion history and exports or forgets it. An optional deterministic worker creates at most one current eligible task per routine/pass, with an optional private in-app reminder. No model, provider, calendar write, external notification or production activation occurs. ORG-03/CORE-11/REM-01 advance within existing task scopes; complete recurring/external delivery acceptance remains open.

## Clarify / design checklist

- Existing household_shared/member_a_private/member_b_private scopes only. Shared readers see current routines/tasks; creator alone changes a routine or reads its history/occurrences/exports. Private needs creator plus current membership; admin is not a content grant. Routine/task/reminder ownership and scopes cannot change.
- Rules are daily or weekly with an interval of 1–4 days/weeks; weekly uses explicit ISO weekdays 1–7, aligned to the Monday of the start week. Inclusive start/end dates span at most 366 days; one local HH:MM per eligible date, explicit IANA zone. No monthly/holiday/exception/rule-text engine, calendar coupling or delegated recipient is implied.
- Preview and save use the same bounded local resolver. DST folds choose the earlier real instant; nonexistent local times are skipped explicitly, not shifted; no floating times. Store UTC instants plus local dates/zone and immutable plan provenance. A saved/corrected/resumed plan starts strictly in the future and never backfills time before that action. Preview is advisory; save revalidates against server time. Correction affects future creation only, not existing task content/status.
- Stable occurrence identity is routine UUID + local date, independent of schedule version. A correction cannot create a second task for an already materialized date. Persist cursor and unique metadata receipts atomically with task/history/optional reminder and system audit; concurrent/restarted workers cannot repeat an effect in one database timeline. Uncertain HTTP results require explicit reload, no automatic mutation retry.
- After downtime, materialize only the latest due slot if no more than 24 hours late; record earlier due slots as missed. No backlog flood, silent completion or inferred adherence. DST gaps remain explicit in the stored plan; skipped receipts are recorded when advancing to the next due real slot. Trailing gaps stay visible in the finite plan, without prematurely reserving their dates. At most 100 candidate routines/pass and one task/routine/pass; future/paused/finished/blocked/forgotten routines cannot generate. Current active owner and selected grant are rechecked under exclusive user, membership and routine locks through commit. Normal browser-session expiry does not revoke persisted intent; owner/grant revocation blocks it until explicit authorized resume.
- Pausing stops creation and cancels active reminders linked to generated tasks; existing task content/status stays unchanged. Resume builds a future-only plan and never reactivates old reminders. Correcting also cancels old active linked reminders before a future plan replaces the cursor. Completion is the existing task's current structured status/history; acknowledging a reminder does not complete it. Reminder opt-in explicitly authorizes creator-private in-app availability, not phone/email or proof of reading.
- Generated reminders use the existing preference/quiet/day-budget/delivery worker; schedule one second after task generation, independent of original task due time, preserving its future-scheduling SQL guard. Metadata records owner authorization and actual routine-worker initiation. No worker runs on a web request; both services remain opt-in/stopped by default.
- Limits: 10 total routine identities/creator including tombstones, 100 human changes/routine, 400 occurrence receipts/routine, at most 366 slots/plan; bounded history (5 revisions/page) and occurrences (25/page). Hit limits blocks further generation/change with explicit status; pause/forget remain available. No long-term capacity claim.
- Forget atomically stops future creation, scrubs routine/current historical payloads and every generated task/current historical payload, cancels active linked reminders, and preserves only scheduling/identity/audit receipts. Old downloaded/provider/backup copies are outside recall. Export/history require current creator authority; downloads require explicit unmanaged-copy acknowledgement. An older restore can reintroduce intent: consumers stay stopped until reviewed recovery; this is not cross-restore deduplication.
- Human reads/writes: HTTPS/Host/Origin/CSRF/current session/grant and expected revision. Lock order user → membership → routine → generated tasks in stable ID order → reminders; audit commits before protected response/effects release. Recheck expiry after waits/long operations; audit failure rolls back the entire aggregate. Audit/logs never contain titles/details/source references or full plans. Browser drafts/history remain in memory, clear on scope/view/session/denial; late responses cannot repopulate them. No model or provider I/O.

## Acceptance

1. Daily/weekly interval/weekday/end rules; forward-only preview/correction/resume; DST gap/fold and 23/25-hour changes; finite quotas and stable local-date idempotence.
2. Task/private-reminder generation, missed/gap receipts, actual current task completion/corrections, pause/correct cancellation and aggregate forget/history/export.
3. Scope/private/admin/CSRF/origin/session/current-grant negatives; after-wait expiry, real concurrency, worker revocation, crash/audit rollback, immutable database identity/history and least privilege.
4. Actual disposable PostgreSQL migration down/up and full logical restore retain plans/receipts/task/reminder lineage and terminal forgotten scrubbing. Older-restore consumers remain manually gated.
5. Responsive trusted-HTTPS browser lifecycle/preview/history/export/forget, conflict drafts and late scope changes. Synthetic fixtures use dedicated accounts in an existing fresh phase without weakening login limits.
6. Required make check, security/dependency/privacy/149-ID parity and coherent canonical docs; one commit/PR. After publishing, stop and tell the owner which CI results to expect; no polling or auto-merge.
