# Publication boundary

This candidate is a clean source snapshot prepared for a **new** repository. The existing private repository and its old branches, issues, PR discussions, CI logs/artifacts and commit-author history are not included. No repository visibility, remote, billing configuration or deployed service is changed by creating this folder.

Public content includes source, synthetic tests, migration/permission logic, generic technical guides and generic protocol identifiers, display names and scope descriptions. This is an intentional API/database namespace change for a new codebase. It is not a drop-in update for existing private installations; no private database or deployment is converted. Role setup checks for generic scopes before mutating roles.

Historical planning, personal/domain/host notes, owner billing reports and acceptance evidence are excluded or replaced by generic documentation. Generated files make no claim of new public CI, production readiness or independent owner-host acceptance. Dependencies remain locked and their notices remain. No new open-source license is granted by this preparation.

Before publication, review the exact file list and confirm the destination/audience and license decision. Start with fresh no-reply commit metadata. Never push the old private branches or use a mirror push. Do not enable production secrets/privileged workflows in a public repository. Run the complete required checks on the new source head after publication, while keeping production/data activation separately gated.

Online migrations also reject an existing scope table without the generic namespace before executing migration DDL. This is a refusal, not a conversion tool. Review any offline SQL manually; publishing code does not authorize changes to an existing installation.

Personal scope choices are explicitly preferred when granted; generic identifier spelling cannot make a new form default to shared visibility. This is a presentation default, not an additional permission grant.
