# Everyday MVP acceptance

This is the acceptance contract for CORE/ORG/DOC/REM/UI foundations, basic FIN-06, OPS-09/10, RND-01 and MVP-01–05 in the [register](FEATURE_REGISTER.md). It does not declare an accepted MVP. Every scenario needs an executable feature test or reviewed host procedure, exact revision, result and limitations. Synthetic adapters establish engineering behavior; they do not certify live services.

## Gates for claiming acceptance

- Feature specs define numerical parser/model/resource/delivery thresholds before implementation; unresolved thresholds are not passing evidence. Required negative permissions, prompt/tool, audit, concurrency, migration, retry/idempotency and restore paths must pass.
- Data-flow declarations name what leaves the environment for every adapter. Providers, accounts, recipient mapping, source permissions, retention and standing write/send rules require review before real activation. Local manual/synthetic fallbacks do not close live-provider gates.
- Encryption at rest/in transit/in backups, key rotation/revocation/recovery, access review, independent alerting, capacity and upgrade/rollback are checked in reviewed runbooks. Candidate RPOs are at most one hour for critical manual records and 24 hours for bulk documents/configuration; candidate RTO is four hours with a prepared compatible host, otherwise next-day/manual recovery. These remain proposals until measured and accepted.
- CI must pass the conservative scope policy and mandatory final gate at the PR head. Production/package certification separately requires successful full coverage on the exact main revision, independently reviewed deployment/security/recovery procedures and host acceptance. A narrow documentation run certifies no runtime behavior.
- Review/merge is performed by the owner. Track branch verification, merged delivery, host/provider acceptance and release certification separately. No feature is marked Done from this planning PR alone.
