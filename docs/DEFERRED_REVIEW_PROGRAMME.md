# Approved deferred review and refactoring programme

Approved on 9 November 2026, recorded in [PR15's owner decision](https://github.com/LYF-FC/local-assistant-core/pull/15). All recommendations in the [individual and whole-product review](FEATURE_REVIEW.md) are part of the project. Implement this programme **after the existing agreed scope, including its later stages**. This scheduling decision supersedes earlier review suggestions to move particular care/asset work earlier or otherwise change priorities. Existing milestones and acceptance gates remain in force; no new version number or date is promised.

## Complete programme, not only the six additions

The programme includes each of the 149 baseline assessments, the sixteen shared implementation boundaries and all ten whole-product observations. The original review is the per-reference checklist; do not duplicate149 tasks or silently retain only the A–F additions. Keep the existing 41 Keep/31 Generalize/52 Consolidate/16 Validate/9 Challenge mapping for these baseline entries.

| Review workstream | Required later treatment |
|---|---|
| Keep | Verify that the retained outcome and boundary still hold; do not invent a mandatory rewrite when the existing implementation already satisfies the review. |
| Generalize | Remove unnecessary fixed-household/vendor assumptions behind reviewed configuration/adapter contracts, retaining original use cases, identity and provenance. |
| Consolidate | Refactor repeated machinery into shared contracts where justified; preserve domain stores, grants, audit, exports and each original acceptance outcome. No universal global-memory store or scope merger. |

| Shared implementation map | Reconcile all sixteen review rows: identity; source/audit/export/retention; attention/search/briefing; tasks/notifications; document intake; file-change manifests; assets; inventory; care; offline education; people/projects/decisions; creative flows; finance; bounded collection; real-effect authority; DMARC. Keep each stated separation boundary. |
| Whole-product review | Reassess usable vertical workflows/UI, configuration, vendor generalization, measured AI complexity, domain timing, parser limits/corpus usefulness, understandable forgetting and stage/count reporting. Existing implementation obligations remain baseline work; the later programme is an improvement/consolidation pass, not permission to delay them. |

Before refactoring, map every affected feature/spec to its current behavior, intended improvement and retained acceptance. Define compatibility, data migration/rollback when relevant, negative permission tests and recovery/export evidence. Group related implementation changes into coherent batches. Accept existing correct behavior without unnecessary rewrites; retire duplicate code only after equivalent behavior and boundaries are proved. Review suggestions are approved directions, not an automatic licence to drop features or select an untested architecture.

## Ordering, gates and evidence

“After existing scope” means a later programme following the original149-reference implementation plan and its later-stage acceptance/conditional research decisions. It does not make completion of every distant feature a condition of an earlier MVP/release, force adoption of infeasible research, or require activating real services without authorization. Dependencies can be designed in baseline work where already required; the newly approved expansion/refactoring programme stays deferred. Existing security, accessibility, privacy and recovery requirements cannot be postponed by this decision.

All new references are planned, with first stage **After existing scope · Approved review programme**. No v1.2 allocation is inferred. Detailed specifications must establish numerical bounds, owner-facing acceptance, dependencies, data/permission effects and migration/recovery plans before implementation. Keep synthetic data and existing constitution boundaries. Separate authorization is still required for live integrations, model/provider/production activation, private-data access and private migration. No data leaves the private environment and no deployment is changed by this documentation batch.

Track completion against original acceptance plus the reviewed refinements; distinguish implementation, accepted user journeys and full retained contracts. Approval is not delivery.
