# Recurring routines — spec 055

Recurring routines add finite daily/weekly task creation to the manual agenda and creator-private in-app reminders. They use structured state and an optional local worker, with no model, external messaging, calendar write or real integration. This is a bounded ORG-03/CORE-11/REM-01 foundation; monthly/holiday/exception rules, delegated recipients, calendar coupling and external notification acceptance remain open.

## Preview, authorize and use

Open **Recurring routines**, choose an assigned shared or creator-private task scope, then **New routine**. Enter the template/source, explicit IANA timezone, local HH:MM, daily or weekly frequency, interval 1–4, inclusive first/last dates, and optional private reminder. Weekly rules select distinct ISO weekdays, aligned to the Monday of the start week. A finite plan spans at most 366 dates. First date must be today or later; save requires at least one future real occurrence.

**Preview routine plan** resolves local dates to UTC and shows skipped nonexistent times. Review and explicitly authorize future task creation plus the chosen reminder option, then save. Preview expires within one minute/session expiry; save revalidates server time. Changing a field invalidates preview/authorization. Source text remains inert; no rule text can invoke tools.

DST folds choose the earlier real instant. Nonexistent local times are skipped, not shifted. Their dates remain explicit in the immutable plan; a skipped receipt is recorded when the worker advances through a gap to a due real slot. Trailing gaps stay visible in the plan when there are no further real slots. Future gap dates are not prematurely reserved, so a correction can replace them. Plans retain UTC instants plus original local dates/zone; the locked timezone database is part of the runtime provenance.

Shared members read current routine/task content. Only the creator changes the routine or inspects history/occurrences/downloads; private content also requires current membership. Administration does not grant private access. Existing fixed household scopes remain unchanged; this does not implement INSTALL flexible identities.

## Generation and completion

Saving authorizes local future creation, not starting the worker service. When due, the optional routine worker locks current owner/membership/routine, creates a task with its normal revision/history, records a unique routine/local-date receipt and advances the cursor in one audited transaction. The receipt links the task and original routine revision. Stable task/receipt identities and a unique local-date constraint prevent repeated/concurrent processes from creating the same effect in one database timeline, even after a schedule correction.

After downtime, only the latest due real slot can create a task, and only if at most 24 hours late. Earlier due dates are recorded missed; no backlog flood, silent completion or inferred adherence occurs. A pass considers at most 100 due routines, creating at most one task per routine. Current inactive/revoked owners block generation; restoring a grant alone does not restart a blocked plan. The creator must explicitly resume it under current authority. Saved worker intent does not depend on a browser session remaining open.

Complete/correct generated tasks in **Tasks and agenda**. **Inspect occurrences and completion** resolves their current structured status; normal task history remains authoritative. Reminder acknowledgement is not task completion. A routine source reference in the generated task and occurrence's routine revision preserve lineage; generated tasks do not copy a separate authoritative completion store.

An opted-in reminder is private to the creator even for a shared task. It is scheduled one second after generation, independently of the original task due time, preserving the existing future-scheduling SQL guard. Existing reminder preferences, quiet hours, day budgets, history and delivery worker apply. Reminder events record owner authorization; metadata audit identifies actual routine-worker initiation. Delivered means available in Butler, not phone/email delivery or proof of reading.

## Correct, pause, resume and forget

**Correct future routine** previews/re-authorizes a new future-only plan. Existing task content/status is unchanged; any already materialized local date keeps its receipt and cannot generate again. Choose today or later when correcting; this is an explicit replacement schedule, not a hidden rewrite of past dates. **Pause routine** stops future creation and cancels active linked reminders, retaining tasks and history. Correction also cancels old linked active reminders before replacing future intent. **Resume future routine** preserves the original rule alignment but excludes elapsed dates; it never backfills the paused interval or reactivates old reminders. Independently rescheduling an existing task reminder remains an explicit separate intent.

Quota bounds are 10 routine identities/creator including forgotten tombstones, 100 human changes/routine and 400 unique occurrence receipts/routine; revision safety reserves the final transitions for blocking/pause/forget. Each plan contains at most 366 slots. Quotas block further generation/change with visible blocked state or a sanitized limit refusal. Pause/forget remain available as applicable. These development limits require a reviewed retention/capacity design before long-running adoption; forgetting does not free an identity quota or recall unmanaged copies.

**Forget routine and generated tasks** atomically stops creation, scrubs its current/all historical payloads and every generated task/current historical payload, and cancels active linked reminders. Minimal identity/date/outcome/task-reference and scheduling/audit receipts remain; they contain no copied title/details/source text. Closing or forgetting one generated task independently does not stop the routine's other future dates. Old exports/backups/provider originals cannot be recalled.

History is creator-only, five revisions/page. Occurrences show 25 local dates/page and current authorized task status. Download requires explicit unmanaged-copy acknowledgement and freshly reauthorizes a five-revision history page plus the first 25 occurrences/current tasks, with cursors. The API export also accepts `after_date` to select another occurrence page. This is a live bounded download, not an entire collection or globally coherent backup. Forgotten history remains scrubbed.

## Worker and recovery boundary

Migration `0027_recurring_routines` adds `routines`, `routine_revisions`, `routine_occurrences`, their indexes/guards and restricted runtime grants. Apply through the existing privileged migration role and matching restricted-role setup. Ordinary identity changes, revision jumps, history rewrites, receipt duplication and delete/truncate are denied. Platform tables use application-level owner/scope enforcement; no per-user RLS claim is introduced.

The new `routines` Compose profile runs `python -m app.routine_worker --once` or `--loop` with restricted development/test credentials, data network only, non-root/read-only/capability-dropped limits. The normal stack starts neither routine nor reminder worker. Both remain independent opt-in services; no existing private deployment is activated by code or tests. Counts-only output omits identifiers, source text, SQL and credentials. Atomic rollback permits retry after a pre-commit crash; there is no external delivery effect or provider receipt.

Stop both consumers before update/restore. Logical backups include plans, sealed revisions, occurrence receipts and linked task/reminder records; the restore drill verifies paused plans, lineage, immutable IDs and aggregate forgotten scrubbing. An older database can reintroduce later-cancelled/generated intent: keep consumers stopped until current authority, pending intent, capacity and recovery are explicitly reviewed. This feature is not a cross-restore deduplication ledger, startup fence, clean-host certificate or production acceptance. Downgrade removes routine/receipt/history tables but leaves ordinary generated tasks/reminders: review protected backup and rollback/lineage limits rather than downgrading populated systems casually.

Human paths require HTTPS/Host/Origin/CSRF/current session/grant and optimistic revision. User → membership → routine → stable-ordered tasks → reminders locks cover state/history/audit commit. Session expiry after waits prevents release; expiry during a long aggregate rolls it back. Metadata-only audit excludes template/source text and whole plans. Browser drafts/results/history stay in memory and clear on scope/view/session/denial; aborted/late responses cannot restore an old view. No automatic mutation retries, network client, model or secret is introduced. Only explicit JSON download creates an unmanaged local copy.
